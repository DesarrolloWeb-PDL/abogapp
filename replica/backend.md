## What is done

### 1. Env contract (`.env.example`, names only)

| variable | scope | used by |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | public | browser client, server client, proxy, service client |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | public | browser + server clients (RLS is the guard) |
| `SUPABASE_SECRET_KEY` | **server only** | `lib/supabase/service.ts` → WhatsApp webhook writes |
| `DATA_DRIVER` | server, optional | `supabase` \| `fake` override |

`.gitignore` already covers `.env*` with the `.env.example` exception; real
values belong in `.env.local` (never committed, never generated by the
agent). Verified: no `SERVICE_ROLE` reference under `app/`/`components/` and
none in any built client chunk (`.next/static`).

### 2. Migrations + seed (`supabase/`)

- `migrations/20261114120000_init.sql` — all **48 tables**, every index,
  check/unique constraint, trigger, RLS policy and the four storage policies
  from `replica/schema.sql` (the read-only source of truth), converted to
  **idempotent** DDL (`create … if not exists`, `drop … if exists` before
  triggers/policies, guarded DO blocks). Supabase-specific adjustments:
  - `f_unaccent` resolves where `unaccent(text)` actually lives (`public` or
    `extensions`) instead of assuming `search_path`;
  - the three `gin_trgm_ops` indexes are created in one guarded block that
    points `search_path` at the pg_trgm schema first;
  - explicit `grant`s to `anon`/`authenticated`/`service_role` (+ default
    privileges) so RLS can filter instead of failing with permission denied;
  - the `documents` storage bucket is inserted (private), with a graceful
    notice if the role lacks storage privileges — create it by hand then;
  - `auth.users` trigger (`on_auth_user_created` → `profiles`) kept — it is
    Supabase's documented pattern;
  - unique FK-target `uq_cases_id_study` kept as a **constraint** (guarded by
    pg_constraint check) because child composite FKs need a constraint, not a
    bare index.
- `seed.sql` — one portable DO block (no psql variables; runs in the
  dashboard SQL Editor): two demo auth users (example.com, fake password
  printed in the file), a study with the wizard's `init_study_defaults`
  membership path, 2 cases, 1 person, 2 pruebas + trigger-computed plazos,
  1 unread notification, and a WhatsApp contact/conversation/message thread.
  Idempotent (fixed UUIDs + `on conflict do nothing`), and it **skips
  entirely** if `auth.users` already holds non-seed accounts.
- **How to run (no CLI installed yet):** paste each file into the Supabase
  dashboard **SQL Editor** (migration first, then seed). Later,
  `npx supabase db push` works too (`supabase/migrations/` follows the CLI
  convention; `seed.sql` maps to `supabase/config.toml`'s seed once the CLI
  is initialised).
- Both files were parse-validated with libpg_query (PostgreSQL's real
  grammar: 280 statements + the seed DO block). **Semantics (permissions,
  triggers, auth schema shape) still need the live run.**

### 3. Supabase clients (`lib/supabase/`)

| file | runs on | role |
| --- | --- | --- |
| `client.ts` | browser | `createBrowserClient` — anon key, RLS boundary |
| `server.ts` | server | `createServerClient` + async `await cookies()` (Next 16) with `getAll`/`setAll` |
| `session.ts` | server (proxy) | token refresh + optimistic redirects |
| `service.ts` | **server only** | service-role client; throws if called in a browser |
| `inbox.ts` | server | RLS-scoped `wa_conversations`/`wa_messages` reads |
| `meta-webhook.ts` | server | service-role webhook writes (idempotent on `event_key`) |
| `studies.ts` | browser | wizard path: insert study + `init_study_defaults` RPC |

- `proxy.ts` (project root) — **Next 16 renamed middleware to proxy**; it
  refreshes the session before any page runs and redirects
  unauthenticated users off protected pages (auth pages redirect signed-in
  users to `/expedientes`). API routes are never redirected (they answer
  401/503 as JSON). Fake driver (no keys) → proxy passes through untouched.
- Cookie reality check (verified in `@supabase/ssr@0.12.7` source):
  `DEFAULT_COOKIE_OPTIONS` is `httpOnly: false, sameSite: lax, path: /` —
  the library **cannot** use httpOnly session cookies because the browser
  client must read them to refresh tokens. Our clients add
  `secure` in production. Mitigations: RLS everywhere, server-side
  `getUser()` in the proxy and routes, service key never near the client.

### 4. Auth — same signatures, driver switch (`lib/data/`)

- `DATA_DRIVER` rule (`lib/data/driver.ts`), in order:
  1. `DATA_DRIVER=supabase|fake` explicit value wins;
  2. else both `NEXT_PUBLIC_*` vars present → `supabase`;
  3. else → `fake` (unit tests and `next dev` without `.env.local` keep
     working — this is the default).
- `lib/data/auth.ts` keeps the exported contract (`signUp`, `signIn`,
  `signOut`, `getSession`, `updateProfile`, `requireSession`, the outcome
  types) and dispatches to `auth-fake.ts` (in-memory demo) or
  `auth-supabase.ts` (Supabase Auth). Shared validation runs before either
  driver, so bad input never reaches the network.
- Supabase flow: email/password **with verification** — sign-up that returns
  no session maps to `confirmation_pending` (the signup form shows a
  "revisá tu correo" notice, not an error); sign-in before confirming maps to
  `email_not_confirmed`; `email_taken` / `invalid_credentials` /
  `too_many_requests` / `save_failed` map from GoTrue messages. Magic link
  was **not** built: the recon shows the original has no magic-link login.
- **Study membership path the wizard uses:** `createStudy` (supabase
  driver) inserts the study with `created_by = auth.uid()` (RLS-checked) and
  calls `init_study_defaults(study_id, user_id)` — the migration's
  security-definer function that creates the Dueño role, the owner's active
  membership and the five default task statuses. `getMyStudy` reads
  `memberships → studies` under RLS. The `on_auth_user_created` trigger
  creates the profile row at sign-up.
- Session wiring: browser client for UI reads/writes (cookies), `proxy.ts`
  for refresh + optimistic redirect, route handlers for server checks.
  `AuthGuard` now resolves the session through `getSession()` (driver-aware)
  and the sidebar signs out through the data layer (clears Supabase cookies
  too). Boundary: `getSession()` answers `null` on the server in the
  supabase driver **on purpose** — server session reads must use
  `lib/supabase/server` (importing `next/headers` into a client-reachable
  module would pollute the client bundle).

### 5. Security items closed (from `build-log.md` → Open items)

1. **`GET /api/wa/conversations` now requires a valid session → 401
   otherwise** (both drivers: supabase = `getUser()` on request cookies +
   RLS-scoped query; fake = store session or the demo cookie the fake layer
   writes on sign-in, because localStorage never reaches a route handler).
   Tested (see below).
2. **Demo credential pair hidden with real auth:** `login/page.tsx`
   computes `showDemoHint = getDataDriver() === "fake"` server-side and
   passes it to the form — with Supabase keys present the seed credentials
   never render.
3. **Webhook writes use the service-role key server-side only:**
   `processInboundMeta` (imported only by `app/api/webhooks/whatsapp`)
   claims each Meta delivery in `wa_webhook_events` (unique `event_key`,
   23505 → counted duplicate, failure → row deleted so the retry
   reprocesses — same semantics as the fake `markEventProcessed`/
   `releaseEventKey`), then upserts contact/conversation, stores both
   messages and answers with the shared bot rules (`lib/data/bot.ts` — one
   implementation for both drivers). The reply is not local anymore: it is
   delivered through the Graph API when `WHATSAPP_ACCESS_TOKEN` exists
   (recorded `not_configured` otherwise, WhatsApp Unit 2) and, only when no
   rule matches, `resolveBotReply` may answer through an env-gated LLM
   (`AI_API_KEY`, WhatsApp Unit 3) — rules always run first, and any model
   failure falls back to the default rule reply. The `wa_webhook_events`
   table (RLS on, no policies → service role only) is in the migration.
   The in-memory-store multi-instance gap (open item 3) is closed for the
   supabase driver: persistence now lives in Postgres.

## Security checklist (replica-backend skill)

- [x] **secrets only in env vars, `.env*` in `.gitignore`, nothing in client
  bundles** — `.env.example` has names only; `.gitignore` ignores `.env*`
  (keeps `.env.example`); greps confirm no `SERVICE_ROLE` under
  `app/`/`components/` and none in `.next/static` chunks. Caveat recorded
  above: `@supabase/ssr` session cookies are `httpOnly: false` by library
  design (browser client must read them); the anon key is public by design
  and RLS is the boundary.
- [x] **input validated on the server on every route** — only two routes
  exist today: the webhook validates `hub.verify_token`, the constant-time
  HMAC signature and every field of the Meta payload before use; the auth
  path re-validates (format + length) before any driver call. No zod yet —
  it arrives with the M2 route layer.
- [ ] **authorisation checked on every read and write, tested with a second
  user** — RLS policies are in the migration and the conversations route
  gates its session, but the second-user test has not run (needs live keys,
  see below).
- [x] **rate limits on auth, sign up, and anything that sends email or SMS**
  — Supabase Auth ships per-endpoint limits (verified in GoTrue docs:
  `Signups` 30/h, password `Token` 150/h, `EmailSent` 30/h, `Verify` 30/h).
  Nothing sends email/SMS yet (Resend not started); app-level/WAF limits
  are a deploy-time task.
- [x] **webhooks verify signatures** — `X-Hub-Signature-256` HMAC-SHA256
  compared in constant time + `hub.verify_token` handshake with no
  hardcoded fallback; 9 unit tests (T8, pre-existing).
- [ ] **uploads: size and type limits, served from a separate domain or
  bucket** — the private `documents` bucket + tenant-folder storage
  policies exist in the migration, but the upload endpoints, 25 MB cap and
  quota trigger wiring are M2/M4 work.
- [x] **no user data in URLs or logs** — no payload/PII logging in routes;
  proxy redirects clear `search`; deep links use record ids only.
- [x] **dependencies audited (`npm audit`)** — run: 10 findings, **all in
  dev tooling** (2 critical in `tinypool`/`vitest` worker pool, 8 moderate
  in `typescript-eslint`→`minimatch`); **zero in production dependencies**
  (`next`, `react`, `@supabase/*`). Non-breaking `npm audit fix` applied
  with no change; the rest needs `vitest@5` (breaking) — deferred
  deliberately: test-runner code never ships and the advisories need a
  malicious local test/mock to trigger.
- [ ] **privacy policy lists every processor** — not written (deploy/legal
  phase; processors so far: Supabase, Vercel at deploy; Stripe/Resend not
  started).

## Pending live verification (needs the user's `.env.local`)

The user creates the Supabase project and pastes the three values into
`.env.local`. None of the following has been run — no live verification is
claimed:

1. **Run the migration** — paste `supabase/migrations/20261114120000_init.sql`
   in the SQL Editor (or `npx supabase db push`). Watch for: extension
   creation rights, the `documents` bucket notice, the `auth.users` trigger.
2. **Run the seed** — `supabase/seed.sql` on a fresh project (it skips when
   `auth.users` already has non-seed accounts). Confirm the GoTrue
   `auth.users`/`auth.identities` insert shape matches the project's schema.
3. **Sign-up / login against real Auth** — confirmation email arrives
   (default "Confirm email" on), `confirmation_pending` notice shows, the
   link lands the user in the wizard; login sets SSR cookies; `proxy.ts`
   refreshes and redirects; sidebar sign-out clears the session.
4. **Wizard → real study + membership** — finish the wizard, then check
   `studies` + `memberships` (active) + `roles` (Dueño) + `task_statuses`
   rows exist; `getMyStudy` returns the study.
5. **RLS second-user test** — sign in as the seed's outsider
   (`outsider@example.com`): must read **zero** rows of study 1 (studies,
   cases, wa_conversations…). This ticks the authorisation checklist row.
6. **Webhook end-to-end** — `GET` handshake with `WHATSAPP_VERIFY_TOKEN`,
   `POST` a signed payload (HMAC with `WHATSAPP_APP_SECRET`): one row in
   `wa_webhook_events`, conversation + messages written through the service
   role, the retry of the same payload counted as a duplicate, and
   `GET /api/wa/conversations` showing the row under a real session (401
   without one).
7. **Demo-hint check** — with keys present, `/login` must not render the
   seed credential pair.
